# Backend WebSocket Protocol

This document describes the backend WebSocket/STOMP protocol verified against
`SE2-Machi-Koro/Server` on `main` at commit `f0b5ccf`.

It is intended as the client-facing protocol reference for Sprint 3 review and
for validating the current backend networking behavior.

## Connection

| Transport | Endpoint | Intended usage |
| :--- | :--- | :--- |
| Native WebSocket STOMP | `/ws` | Android and native STOMP clients |
| SockJS STOMP | `/ws-sockjs` | Browser and manual testing fallback |

The backend enables the simple broker for `/topic` and `/queue` destinations.
Application messages must be sent to destinations prefixed with `/app`.

Default allowed origins are:

```text
http://localhost:8080,http://localhost:3000
```

The allowed origins can be overridden through the backend property
`websocket.allowed-origins`.

## Client Subscriptions

| Subscription | Scope | Current usage |
| :--- | :--- | :--- |
| `/topic/public` | Global room/chat/game phase channel | Chat join/send/leave messages, phase updates, and game end broadcasts |
| `/topic/game/{gameId}` | Game-specific channel | Effect resolution result and finished-game player leave event |
| `/user/queue/errors` | User-specific error queue | Structured errors emitted by `GlobalWebSocketExceptionHandler` |

Game-specific state messages should prefer `/topic/game/{gameId}` when the
backend handler has a game id available. The current backend still broadcasts
phase changes and game end events on `/topic/public`.

## Message Envelope

Most broadcast messages use the `WebSocketMessage` envelope:

```json
{
  "type": "GAME_ACTION",
  "sender": "server",
  "content": null,
  "payload": {
    "turnPhase": "RESOLVE_EFFECTS"
  },
  "timestamp": 1714000000000,
  "gameId": null
}
```

| Field | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `type` | `MessageType` | Yes | Message category. |
| `sender` | String | Yes | Sender identifier, usually `server` for backend messages. |
| `content` | String or `null` | No | Optional text content. |
| `payload` | Object, scalar, or `null` | No | Structured event-specific data. |
| `timestamp` | Long | Yes | Unix timestamp in milliseconds generated by the backend if omitted. |
| `gameId` | Integer or `null` | No | Game id attached by the sender when relevant. |

## Message Types

The current backend enum contains these values:

| Type | Current meaning |
| :--- | :--- |
| `CHAT` | Chat message sent through `/app/chat.send`. |
| `JOIN` | User join message sent through `/app/chat.addUser`. |
| `LEAVE` | Disconnect notification broadcast by the backend listener. |
| `GAME_START` | Defined in the enum, but no WebSocket `/app/game.start` handler exists on current backend `main`. |
| `GAME_ACTION` | Generic game action broadcast, including phase changes and effect resolution. |
| `GAME_END` | Winner notification. |
| `PLAYER_LEFT_FINISHED_GAME` | A player left an already finished game. |
| `ERROR` | Error message sent as a `WebSocketMessage` by selected handlers. |

The issue text mentions `GAME_STARTED`, `ROLL_DICE`, and `SYNC`, but those
message types are not present in the current backend enum. Clients should not
depend on them until the backend contract is implemented.

## Application Destinations

### `/app/chat.addUser`

Registers the sender name in the WebSocket session and optionally adds an
existing user to a lobby when `gameId` is provided.

Request:

```json
{
  "type": "JOIN",
  "sender": "alice",
  "content": "Alice joined",
  "gameId": 1
}
```

Broadcast destination:

```text
/topic/public
```

Broadcast response:

```json
{
  "type": "JOIN",
  "sender": "alice",
  "content": "Alice joined",
  "payload": null,
  "timestamp": 1714000000000,
  "gameId": 1
}
```

### `/app/chat.send`

Broadcasts a chat message to all subscribers of the public topic.

Request:

```json
{
  "type": "CHAT",
  "sender": "alice",
  "content": "Ready"
}
```

Broadcast destination:

```text
/topic/public
```

### `/app/game.advancePhase`

Advances the persisted turn phase to the next phase.

Request:

```json
{
  "gameId": 1
}
```

Broadcast destination:

```text
/topic/public
```

Broadcast response:

```json
{
  "type": "GAME_ACTION",
  "sender": "server",
  "payload": {
    "turnPhase": "RESOLVE_EFFECTS"
  },
  "timestamp": 1714000000000,
  "gameId": null
}
```

Valid backend phase progression:

```text
ROLL_DICE -> RESOLVE_EFFECTS -> BUY_OR_BUILD -> END_TURN -> ROLL_DICE
```

### `/app/game.resolveEffects`

Resolves income effects for the current dice roll and advances the game to the
buy/build phase.

Request:

```json
{
  "gameId": 1
}
```

Success broadcast destination:

```text
/topic/game/1
```

Success broadcast response:

```json
{
  "type": "GAME_ACTION",
  "sender": "server",
  "payload": {
    "event": "EFFECTS_RESOLVED",
    "gameId": 1
  },
  "timestamp": 1714000000000,
  "gameId": null
}
```

Handler-level failure broadcast destination:

```text
/topic/game/1
```

Handler-level failure response:

```json
{
  "type": "ERROR",
  "sender": "server",
  "payload": {
    "event": "EFFECTS_FAILED",
    "message": "Dice roll not set"
  },
  "timestamp": 1714000000000,
  "gameId": null
}
```

### `/app/game.endTurn`

Ends the active player's buy/build window. If a winner exists, the backend marks
the game as finished and broadcasts a winner event instead of advancing to the
next turn.

Request:

```json
{
  "gameId": 1
}
```

Normal broadcast destination:

```text
/topic/public
```

Normal broadcast response:

```json
{
  "type": "GAME_ACTION",
  "sender": "server",
  "payload": {
    "turnPhase": "ROLL_DICE"
  },
  "timestamp": 1714000000000,
  "gameId": null
}
```

Winner broadcast destination:

```text
/topic/public
```

Winner broadcast response:

```json
{
  "type": "GAME_END",
  "sender": "server",
  "payload": {
    "winnerId": 7
  },
  "timestamp": 1714000000000,
  "gameId": null
}
```

### `/app/game.leave`

Removes a player from a finished game and broadcasts that the player left the
finished-game view.

Request:

```json
{
  "gameId": 1,
  "playerId": 7
}
```

Broadcast destination:

```text
/topic/game/1
```

Broadcast response:

```json
{
  "type": "PLAYER_LEFT_FINISHED_GAME",
  "sender": "server",
  "payload": {
    "playerId": 7
  },
  "timestamp": 1714000000000,
  "gameId": null
}
```

## User Error Queue

Unhandled `CustomWebSocketException` and generic message-handling exceptions are
sent to the current user session.

Subscription:

```text
/user/queue/errors
```

Custom error response:

```json
{
  "code": "GAME_FINISHED",
  "message": "Game 1 has already ended",
  "timestamp": 1714000000000
}
```

Generic error response:

```json
{
  "code": "INTERNAL_ERROR",
  "message": "Unexpected error while processing WebSocket message",
  "timestamp": 1714000000000
}
```

## REST Start Game Endpoint

Game start is currently exposed as REST, not WebSocket.

```http
POST /lobby/{gameId}/start
```

Example:

```http
POST /lobby/1/start
```

Successful response:

```http
200 OK
```

Failure response:

```http
400 Bad Request
Content-Type: text/plain

Game with id 1 not found
```

There is no current backend WebSocket handler for `/app/game.start`.

## Destinations Listed In Issue 23 But Not Present On Backend Main

The following destinations are listed in the documentation issue but are not
implemented in the current `SE2-Machi-Koro/Server` `main` branch:

| Issue-listed destination | Current status |
| :--- | :--- |
| `/app/game.start` | Not present. Use `POST /lobby/{gameId}/start`. |
| `/app/game.rollDice` | Not present. Dice persistence exists in DAO methods, but no WebSocket controller mapping is exposed. |
| `/app/game.purchase` | Not present. A remote branch named `origin/60-implement-purchase-handling-validation-and-execution` exists, but this contract is not on `main`. |
| `/app/game.sync` | Not present. No `/user/queue/game-sync` producer is exposed on current backend `main`. |
| `/user/queue/game-sync` | Not present in current backend message handlers. |

Because these handlers are absent, this document intentionally does not define
request or response payloads for purchase or sync. Adding example payloads before
the backend exposes DTOs would create an inaccurate client contract.

## Reconnect Behavior

Current backend `main` stores the WebSocket username in the STOMP session when
`/app/chat.addUser` is received and broadcasts a `LEAVE` message to
`/topic/public` when a session disconnects.

The issue text references reconnect recovery via `/app/game.sync` and
`/user/queue/game-sync`. Those destinations are not implemented on backend
`main`, so reconnecting clients currently need to reload authoritative game
state through the available REST/data flow until a WebSocket sync handler is
added.

Disconnect broadcast example:

```json
{
  "type": "LEAVE",
  "sender": "alice",
  "content": "alice left",
  "payload": null,
  "timestamp": 1714000000000,
  "gameId": null
}
```

## Demo Verification Checklist

Use this checklist to validate the implemented backend protocol during review:

- Start the backend and connect a STOMP client to `/ws`.
- Subscribe both test clients to `/topic/public`.
- Subscribe both test clients to `/topic/game/{gameId}` for the active game.
- Subscribe each client to `/user/queue/errors`.
- Send `/app/chat.addUser` with a known username and optional `gameId`; verify a
  `JOIN` message on `/topic/public`.
- Send `/app/chat.send`; verify a `CHAT` message on `/topic/public`.
- Send `/app/game.advancePhase`; verify a `GAME_ACTION` phase payload on
  `/topic/public`.
- Send `/app/game.resolveEffects` after a persisted dice roll exists; verify
  `EFFECTS_RESOLVED` on `/topic/game/{gameId}`.
- Send `/app/game.endTurn` during `BUY_OR_BUILD`; verify either a `GAME_ACTION`
  phase update or a `GAME_END` winner payload on `/topic/public`.
- Send an invalid gameplay action; verify a structured response on
  `/user/queue/errors` or an `ERROR` envelope on `/topic/game/{gameId}`,
  depending on which handler rejects the request.
